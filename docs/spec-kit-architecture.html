Spec-Kit Architecture & Usage Guide

Spec-Driven Development for StayWiseAI — how the toolkit is wired and how to drive it end to end.

What is Spec-Kit

Spec-Kit is GitHub's toolkit for Spec-Driven Development (SDD): instead of prompting an AI agent to "just build it," you build software in disciplined, reviewable phases. Each phase produces a durable Markdown artifact that the next phase consumes. The intent, not the code, is the source of truth.

The core idea encoded in this repo's constitution.md is a strictly linear pipeline:

/constitutionProject rulesconstitution.md
→
/specifyThe whatspec.md
→
/planThe howplan.md
→
/tasksThe work listtasks.md
→
/implementThe codesrc/**
In StayWiseAI the linear order is constitutional law: "Skipping phases is not allowed. If implementation reveals the spec is wrong, update the spec first before continuing." (constitution.md, Process Principles).

System Architecture

Spec-kit is not a runtime library inside your app. It is a layer of prompts, scripts, templates and state files that sits between you, your AI coding agent (GitHub Copilot here), and your repository. The agent reads the prompts and templates; the scripts do the deterministic file/branch plumbing; the state files track which feature is active.

Control flow of a single command

When you invoke a command such as /speckit.specify, this is what fires:

# 1. Copilot loads the prompt definition
.github/prompts/speckit.specify.prompt.md

# 2. Pre-hook fires (from .specify/extensions.yml → before_specify)
git extension → speckit.git.feature   # create feature branch 001-...

# 3. The prompt tells the agent to run the scaffolding script
.specify/scripts/powershell/create-new-feature.ps1
   → creates .specify/specs/001-housing-recommendations/
   → copies spec-template.md → spec.md
   → updates .specify/feature.json  (active feature pointer)

# 4. Agent fills spec.md from your description + the template structure

# 5. Post-hook fires (after_specify)
git extension → speckit.git.commit      # optional auto-commit
Separation of concerns: the AI never invents file paths or branch names. The PowerShell scripts own all filesystem and git side effects deterministically; the agent only fills in content. That is what makes the workflow reproducible.

Git Extension & Hooks

This repo installs the git extension (.specify/extensions.yml → installed: [git]) with auto_execute_hooks: true. It binds git actions to lifecycle points around every phase.

Required hooks

  • before_constitution → git.initialize (sets up the repo)
  • before_specify → git.feature (creates the NNN-feature branch)

Optional auto-commit hooks

A git.commit hook runs before and after clarify, plan, tasks, implement, checklist, analyze, and taskstoissues — each prompts you first, so every phase boundary becomes a clean, revertible commit.

The net effect: each phase produces its own commit, so the git history mirrors the SDD pipeline and any phase can be rolled back independently.

SDD Workflow Engine (one-shot)

Besides running commands one at a time, .specify/workflows/speckit/workflow.yml defines a bundled "Full SDD Cycle" that chains the four core commands with human review gates between them:

specifystep
→
review-specgate · approve/reject
→
planstep
→
review-plangate · approve/reject
→
tasksstep
→
implementstep

Inputs it asks for: spec (what to build), integration (defaults to auto → resolves to copilot), and scope (full / backend-only / frontend-only). A reject at either gate aborts the run, so you never silently flow a bad spec into code.

The workflow requires speckit_version >= 0.8.5 for engine-side resolution of the integration: "auto" default. This repo runs 0.8.17, so it is satisfied.

Step-by-Step: How to Use Spec-Kit

0 · Prerequisites

  1. Confirm the toolchain

    You need GitHub Copilot in VS Code (the active integration), PowerShell (the configured script runtime), and git. Verify spec-kit is wired up:

    # active integration should print "copilot"
cat .specify/integration.json

  2. Open the Copilot chat

    All /speckit.* commands are typed into the Copilot chat panel. Typing / shows the installed commands from .github/prompts/.

1 · Establish the Constitution already done — v1.0.0

  1. Run it once per project

    The constitution is the non-negotiable rulebook every later phase must obey. StayWiseAI already has one (TypeScript strict, named exports only, Zod at every boundary, pure skills, structured LLM output, etc.).

    /speckit.constitution

# Example amendment prompt:
Add a principle requiring all API routes to validate
input with Zod before any I/O. Bump to v1.1.0.

  2. When to revisit

    Only amend it when a durable rule changes. Amendments must bump the version and add a Sync Impact Report entry at the top of constitution.md.

2 · Specify — the what

  1. Describe the feature in plain language

    The before_specify hook auto-creates a numbered feature branch, the script scaffolds the folder, and the agent fills spec.md from the template. Describe behavior and outcomes, not implementation.

    /speckit.specify Build a saved-search feature: a signed-in user can
save the current query and lifestyle filters, name it, and get an
email when 3+ new matching listings appear. Out of scope: SMS alerts.

  2. What you get

    A new .specify/specs/002-saved-search/spec.md with user stories (prioritized P1/P2/P3, each independently testable), functional requirements, success criteria, edge cases, and key entities — mirroring the existing 001-housing-recommendations/spec.md.

  3. Read it before moving on

    The spec is the contract. Look for [NEEDS CLARIFICATION] markers — they signal unresolved ambiguity.

3 · Clarify — de-risk ambiguity

  1. Let the agent interrogate the spec

    The agent asks targeted questions and records each as a Q&A entry under a ## Clarifications session block (see the 5 resolved questions in the housing spec).

    /speckit.clarify

  2. Answer concretely

    Each answer is written back into the spec so downstream phases inherit the decision. Resolve every ambiguity here — it is far cheaper than discovering it during /implement.

4 · Plan — the how

  1. Generate the technical plan

    setup-plan.ps1 scaffolds plan.md; the agent fills it by reading the spec and the constitution. It includes a Constitution Check gate that asserts TypeScript strict, test coverage, and Zod boundaries.

    /speckit.plan Use the existing LangGraph pipeline. Add a Drizzle
table saved_searches, a Postgres-backed cron poller, and reuse the
scoring skill. Email via Resend.

  2. Verify constitutional compliance

    If the plan proposes anything that violates a principle (a default export, an unstructured LLM call, a model instantiated inside a node), fix the plan now.

5 · Tasks — decompose into work

  1. Break the plan into ordered, testable tasks

    setup-tasks.ps1 + the agent turn the plan into tasks.md: a dependency-ordered list where each task is small and independently verifiable.

    /speckit.tasks

  2. Tests are mandatory here

    The constitution overrides the template's old "tests are OPTIONAL" note: "A task is not done until tests pass." Each task should carry its test expectation.

6 · Checklist & Analyze — quality gates (recommended)

  1. Generate a requirements checklist

    /speckit.checklist

    Produces checklists/requirements.md — a verifiable gate that the spec, plan, and tasks are internally complete.

  2. Cross-artifact consistency audit

    /speckit.analyze

    Read-only. Flags drift between spec ↔ plan ↔ tasks (a requirement with no task, a task with no requirement, a constitution violation). Fix findings before building.

7 · Implement — build the code

  1. Execute the task list

    The agent works through tasks.md in order, writing source under src/skills/ (pure functions) and src/graph/nodes/ (orchestration), plus tests, honoring every constitutional principle.

    /speckit.implement

  2. The agent proves completion

    Per the "Tests Prove Completion" principle, stub implementations are rejected — a task closes only on green test output. The after_implement hook offers to commit the result.

8 · Verify — manual gate before "done"

  1. Run the full quality gate

    The constitution's "Manual Verification After Every Implementation" requires all four to pass:

    pnpm test
pnpm typecheck
pnpm build
# + a smoke test: manual UI test (frontend) or LangGraph trace (agent)

  2. Open the PR

    The PR Quality Gate (Principle X) requires pnpm test · lint · typecheck · build to pass in CI, plus a manual smoke test for agent/UI changes, before merge.

Alternative · Run the whole cycle at once

If you prefer the bundled pipeline with built-in review gates instead of typing each command, invoke the Full SDD Cycle workflow. It runs specify → (approve) → plan → (approve) → tasks → implement, pausing for your approval after the spec and after the plan.

Use single commands when you are exploring or the feature is fuzzy (more control, more clarify loops). Use the bundled workflow when the feature is well understood and you want momentum with two safety gates.

Tips & Common Pitfalls

✅ Do

  • Resolve all ambiguity in /clarify before planning.
  • Read each artifact before running the next phase.
  • Let auto-commit hooks run — they make every phase revertible.
  • Treat the spec, not the code, as the source of truth.
  • Run /analyze on anything non-trivial.

⛔ Don't

  • Skip phases — it violates the constitution and breaks traceability.
  • Edit code to fix a spec gap — fix the spec first, then re-flow.
  • Put implementation detail in spec.md (that's plan.md's job).
  • Hand-write TypeScript types — infer them from Zod schemas.
  • Mark a task done without green tests.
Mental model: spec-kit turns "vibe coding" into a reviewable supply chain. Every line of code is traceable backward through a task → a plan decision → a spec requirement → a constitutional principle. When something breaks, you fix it at the highest layer it originates from, then let the change flow back down.
